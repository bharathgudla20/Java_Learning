The details that matter

Orders succeed together

Multi-product stock deduction, order creation, and activity logging run in one database transaction. Insufficient stock rolls back the entire order. Server-side BigDecimal calculations use catalog prices, with price snapshots saved on each order line.

Retries don’t become duplicate orders

Order requests carry an Idempotency-Key. The server returns an existing order when the same workspace retries the same payload, and rejects a key reused for different input. A per-workspace database lock serializes the check and stock mutations.

Cancellation has a boundary

Placed orders can become shipped or cancelled. Cancellation restores stock once. Repeating that same status change is a no-op; switching a terminal status is rejected.

Every workspace owns its data

The server obtains the owner ID from its authenticated session, never the request body. BCrypt protects registered passwords; CSRF protection remains enabled; session cookies are HttpOnly and secure in the hosted profile. Product and order queries are scoped to the owner.

Try a five-minute walkthrough

  1. Open a fresh demo and inspect the low-stock alerts.
  2. Add a new SKU, then increase its stock with a reason.
  3. Place a two-product order and check stock decreases.
  4. Cancel the order and check both quantities return.
  5. Look at the activity history and dashboard updates.

API at a glance

All workspace endpoints require a signed-in session. Unsafe methods require a valid CSRF header. Start with GET /api/auth/csrf; send its token using the returned header name. The complete request/response schemas are in the OpenAPI specification.

What this demo is honest about

The hosted application uses persistent PostgreSQL 17 on Neon. Registered accounts, products, and orders survive application restarts. Sample demo workspaces still expire after two hours. Create a registered account for lasting storage; you may need to sign in again after an application restart.

Local development defaults to an H2 file, with a PostgreSQL profile available. Flyway manages versioned PostgreSQL schema migrations, and Hibernate validates the resulting schema. The integration suite has been run against both H2 and a separate real PostgreSQL branch. The locking strategy prioritizes correctness for a small workload; no high-scale performance claim is made.

There is no payment processing, real shipping provider, or email delivery. Displayed revenue means non-cancelled order value; inventory value means retail value of units on hand.

Why a modular monolith?

One deployable Spring Boot app keeps the API and frontend on the same origin, makes debugging easier, and keeps hosting simple. Microservices would add network failures and distributed coordination before this workload needs them.
